Local development · git worktrees

Implementation plan

One Postgres. A database per worktree.

Keep the existing Compose Postgres on 127.0.0.1:5433. Give each checkout its own DB_NAME, free frontend/backend ports, and matching API/CORS/WebAuthn URLs. Setup and teardown run inside that worktree — no shared daemon, no extra folder, no Testcontainers lifecycle.

First-cut scope. This plan exists to unblock several git worktrees on one machine with the smallest change that actually works. One shared Postgres, one database name per linked worktree, sticky app ports, and printed nx commands. We are not introducing a local orchestrator, per-worktree Compose stacks, Testcontainers-as-dev-DB, a reverse proxy that hides ports, or direnv/Dev Container isolation. Those are normal later upgrades if the service graph grows. The first cut stays simple on purpose.

That shape matches common industry local-dev practice: isolate by catalog not by extra servers, inject env at process start, confirm before DROP, pin Compose project name, keep Testcontainers for tests. Heavier tools (Dev Containers, Tilt, a localhost reverse proxy so WebAuthn always sees port 3000) are valid — they are just more than this cut needs.

What stays shared, what does not

Databases are names on one TCP port. Worktrees never need a registry of who owns 5433.

flowchart TD host[Host loopback] pg[Compose Postgres on 5433] mainDb[Primary database] wtDb[Worktree database] mainUi[Main Vite] mainApi[Main Express] wtUi[Worktree Vite] wtApi[Worktree Express] host --> pg pg --> mainDb pg --> wtDb mainUi --> mainApi mainApi --> mainDb wtUi --> wtApi wtApi --> wtDb

Compose project name, in Docker terms

Docker Compose does not start “Postgres on the machine.” It starts a named project: a private network, containers, and volumes whose names all start with that project id. If you omit -p / COMPOSE_PROJECT_NAME, Compose uses the folder name of the checkout. That is fine for one clone. It is wrong when two git worktrees both run docker compose up.

Without a fixed name

Main folder clean-architecture-backend creates project clean-architecture-backend and publishes host port 5433. Worktree folder feature-auth creates a second project and also tries to publish 5433. Docker refuses: that host port is taken. You now have two attempted Postgreses, not one shared server.

With COMPOSE_PROJECT_NAME=calibrate-shared

Every worktree asks Compose to operate on the same project. The first setup that finds 5433 closed actually starts the container. Later setups see Postgres already accepting connections and skip up. Same network, same volume, same host door 127.0.0.1:5433.

Yes: Compose Postgres + host backend:dev

That split is already how this repo works. Postgres runs in Docker. Express runs on your Mac via npx nx run backend:dev. They meet on the published host port, not on the container-internal name postgres.

Who is connecting Host Port
Another container in the same Compose file postgres (DNS on the Compose network) 5432 inside the container
npx nx run backend:dev, Kysely, psql on your Mac 127.0.0.1 5433 (the mapping in compose.yaml)

Setup will print DB_HOST=127.0.0.1 DB_PORT=5433 DB_NAME=… on the backend command. The Node process then uses the same pg pool it uses today. The container is a real Postgres; API read/write works as long as that env is set when you start backend:dev.

COMPOSE_PROJECT_NAME=calibrate-shared
npx dotenvx run -- docker compose up -d postgres

Setup script

sequenceDiagram participant Dev as Developer in a worktree participant Setup as worktree-setup participant Port as Port picker participant Pg as Shared Postgres :5433 participant Mig as Kysely participant State as .worktree-dev.json Dev->>Setup: run from this checkout Setup->>Setup: copy .env.keys from primary worktree if missing Setup->>Pg: connect with dotenvx DB_USER/PASSWORD alt 5433 closed Setup->>Pg: compose up -d postgres (project calibrate-shared) end Setup->>Setup: derive DB_NAME Setup->>Pg: CREATE DATABASE if missing Setup->>Port: reuse sticky pair or bind-check a new pair Setup->>Mig: migrate:latest with DB_NAME overload Setup->>State: write db, ports, origins Setup->>Dev: print nx commands with env

Env the printed commands must set

Variable Source Who reads it
DB_HOST / DB_PORT Always 127.0.0.1 / 5433 Backend, Kysely
DB_NAME Derived or .env for main Backend, Kysely
PORT Chosen backend port Express
CORS_ORIGIN / WEBAUTHN_ORIGIN http://localhost:<frontend> Backend
VITE_API_BASE_URL http://localhost:<backend>/api/v1 Vite at boot

JWT, OTP HMAC, and email credentials stay in dotenvx. Setup uses dotenvx run --overload --env … so we never set CALIBRATE_E2E=1.

Setup copies .env.keys into the worktree. That file is gitignored, so a new worktree will not have it. Encrypted .env is useless without the key. Before any dotenvx call, setup looks up the primary checkout with git worktree list and copies .env.keys from there if it is missing here. It never commits the key. If the primary has no key either, fail with “set DOTENV_PRIVATE_KEY or copy .env.keys” instead of treating ciphertext as a database password.

Teardown script

Does

  • Read this worktree’s state file (or require --database)
  • Refuse names that are not calibrate_wt_* (and refuse the main .env DB_NAME)
  • DROP DATABASE … WITH (FORCE) so leftover backend connections cannot block it
  • Delete .worktree-dev.json

Does not

  • Stop the shared Compose Postgres
  • Delete the postgres_data volume
  • Drop postgres, template0, or the primary checkout’s existing database
  • Reach into another worktree except to copy .env.keys at setup
FORCE disconnects anyone still on that database. That is the point of teardown after a worktree is done. It must never be aimed at the shared listener itself.

Where the code would live

Phase 1

Shared localhost helpers

One package, two callers. Do not move E2E secrets or worktree DROP DATABASE into it.

  • Create @calibrate/dev-bindings
  • Move canBindLocalhost and selectPortPair out of apps/web-e2e/e2e-runtime.ts
  • Add deriveDevBindings(ports): frontend URL, backend URL, VITE_API_BASE_URL, CORS_ORIGIN, WEBAUTHN_ORIGIN. E2E and worktree-dev both call this so those strings cannot drift.
  • Leave in E2E: Testcontainers, throwaway JWT/OTP keys, CALIBRATE_E2E=1, blank email credential
  • Leave in worktree-dev: .env.keys copy, CREATE/DROP DATABASE, sticky .worktree-dev.json, Compose project name

Phase 2

Setup

Idempotent: safe to re-run in the same worktree.

  • Copy .env.keys from the primary worktree if this checkout does not have it
  • Ensure Postgres on 5433, using COMPOSE_PROJECT_NAME=calibrate-shared only if needed
  • CREATE DATABASE via pg connected to maintenance DB postgres
  • npx dotenvx run --overload --env DB_NAME=… DB_HOST=127.0.0.1 DB_PORT=5433 -- npx nx run backend:kysely migrate:latest
  • Write .worktree-dev.json; gitignore it
  • Print copy-paste backend:dev and web:dev lines with env

Phase 3

Teardown + docs

Destructive, scoped, documented.

  • Nx targets workspace:worktree-setup / workspace:worktree-teardown
  • README: worktree workflow, automatic .env.keys copy, “do not compose down”
  • E2E runtime imports the shared port helpers instead of keeping a second copy

Shared package shape

@calibrate/dev-bindings

In: a frontend/backend port pair. Out: those ports plus frontend URL, backend URL, VITE_API_BASE_URL, CORS_ORIGIN, and WEBAUTHN_ORIGIN. web-e2e and worktree-setup both import this so origin strings cannot drift. JWT minting, Testcontainers, CREATE DATABASE, and .env.keys stay in their callers.

Risks and non-goals

New worktrees lack .env.keys

Setup copies the key from the primary worktree automatically. Still fail closed if neither checkout has it, rather than feeding dotenvx ciphertext to Postgres.

Same folder name, two paths

Basename-only DB_NAME can collide. A short hash of the absolute worktree path belongs in the derived name even if we keep human-readable slugs.

Compose.yaml drift

If two branches change the Postgres service and both call compose up with the same project name, Compose may recreate the container. Setup should skip up when 5433 is already healthy.

Out of scope: per-worktree Redis/mail/object storage, Testcontainers reuse, Dockerizing Vite, or a machine-wide port registry. E2E only switches its port helpers onto the shared package; it does not share Testcontainers or CALIBRATE_E2E setup. Extra Compose services wait until more containers actually need coordinating.
