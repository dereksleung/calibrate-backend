Day Log cache · IndexedDB · activeCache

The cache has a memory, a vault, and a gatekeeper.

day-log-cache.ts keeps confirmed users’ date-scoped Day Logs available across reloads without letting stale, foreign, corrupt, or in-flight data leak into the current QueryClient.

30 days retention window on restore
1 key serialized namespace per user
0 data broadcast across tabs; only clear signals

The short answer

IndexedDB stores the snapshot. TanStack Query serves the working data. activeCache connects exactly one user namespace to one QueryClient.

01 · The mental model

What is actually cached?

The durable layer is one serialized TanStack Query snapshot per user. The in-memory layer contains the individual date queries that the UI reads.

IndexedDB anatomy

createIndexedDbStorage() adapts IndexedDB to the async getItem / setItem / removeItem contract expected by TanStack’s persister.

Database calibrate-day-log-cache
Object store query-cache
User A record calibrate:day-logs:user-a
Stored value { buster, timestamp, clientState }

What passes the persistence filter?

The exact predicate is intentionally narrow: scope dayLogs, one ISO date segment, and a successful query state.

Known-empty is real data. A cached null means “the server confirmed no log for this day”; it remains distinct from an undefined, never-loaded day.
Range and auth state stay out. Range keys and authenticatedSession can live in QueryClient memory, but the Day Log namespace never hydrates them from disk.

02 · Startup and identity

Restore is a guarded activation sequence.

The session gate confirms the user first, then waits for the cache restore before mounting authenticated reads.

One active namespace

activeCache is the gatekeeper

In restoreDayLogCache, activeCache is a local snapshot read from the module-level activeCaches WeakMap.

  • Same user: wait for its ready promise, so concurrent restores do not create duplicate subscriptions.
  • New user: tear down the old descriptor before activating the new user’s namespace.
  • Storage unavailable: keep the user id and a cleanup retry hook, but omit the persister and persistence subscription.
  • Storage available: hold the persister, ready promise, unsubscribe hook, pending write waiter, and BroadcastChannel.

03 · Runtime and teardown

Writes are selective; clears are deliberately ordered.

The module treats persistence as asynchronous work that must be drained before a namespace is deleted.

Normal runtime write

A date query changes; the subscriber takes a filtered snapshot and lets the persister throttle the actual storage write.

Logout or explicit clear

Clearing protects against a late persistence write resurrecting data after logout or an account switch.

stop future writes"] STOP --> WAIT["waitForPendingPersists
drain restore rewrites + writes"] WAIT --> DELETE["persister.removeClient()
delete user namespace"] DELETE --> MEMORY["QueryClient.removeQueries(['dayLogs'])"] MEMORY --> BROADCAST["post { type: 'clear', userId }"] BROADCAST --> CLOSE["close active channel"]

Why the generation number exists

Every restore or clear advances a per-QueryClient operation token. A slow older async operation can finish, but it cannot hydrate or write once its generation is no longer current.

06 · Keep this picture

A private snapshot with a carefully managed lease.

1
QueryClient is the working memory. UI reads individual date queries from here, including values fanned out from a range response.
2
IndexedDB is the durable snapshot. It holds one serialized, per-user record; restore filters and rewrites it instead of trusting it blindly.
3
activeCache is the lease. It says which user owns this QueryClient’s persistence hooks right now and gives teardown a way to stop and drain them.
4
Thirty days is a restore rule, not a timer. gcTime: Infinity keeps restored entries alive in memory; age is enforced when a persisted snapshot is read and sanitized.
