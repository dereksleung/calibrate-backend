How the private Day Log cache works

day-log-cache.ts keeps one user’s date-keyed Day Logs in TanStack Query memory and IndexedDB. This page explains the public functions, the activeCache record, and the restore / persist / logout lifecycle.

What question does this module answer?

After the server confirms who you are, can Dashboard show this user’s recent Day Logs immediately, without waiting on the network, without leaking them to another account on the same browser?

What is activeCache?

It is not the Day Log data. The data lives in the QueryClient (memory) and IndexedDB (disk). activeCache is the per-QueryClient control plane: which user owns this cache, how to persist it, and how to tear it down safely.

The WeakMap

activeCaches maps each QueryClient to at most one ActiveDayLogCache. Garbage-collecting the QueryClient drops the record. There is never “user A and user B” on the same client at once.

Generation beside it

cacheGenerations is a second WeakMap: a monotonically increasing integer per QueryClient. Restore and clear bump it. In-flight work checks isCurrent() and bails if a newer restore/clear started.

Fields on the record

Field Job When it exists
userId Owner of this namespace. Restore no-ops if it already matches. Always
persister TanStack async persister bound to this user’s IndexedDB key. Only when storage opened
ready Promise that resolves when restore has published in-memory data (or given up). Concurrent restore for the same user waits here. During / after restore with storage
clearPersisted Deletes the user namespace. Used even if restore never got a persister. Always once restore ran
unsubscribe Stops writing on query-cache events before logout deletion. After subscribeToPersistence
waitForPendingPersists Awaits in-flight IndexedDB writes so clear does not race a rewrite. With storage
invalidationChannel BroadcastChannel listener for “this user logged out in another tab”. When BroadcastChannel exists

Lifecycle of activeCache

Think of three phases: absent, restoring (record is in the WeakMap, ready still pending), and live (subscribed, writing on Day Log changes). Clear always unsubscribes and waits before deleting disk.

stateDiagram-v2 [*] --> Absent: QueryClient created Absent --> Restoring: restoreDayLogCache new user Restoring --> LiveNoStorage: IndexedDB unavailable Restoring --> LivePersisting: hydrate then subscribe Restoring --> LivePersisting: empty or corrupt disk treated as empty LivePersisting --> Restoring: restore different userId LiveNoStorage --> Restoring: restore different userId LivePersisting --> Clearing: clearDayLogCache or remote logout LiveNoStorage --> Clearing: clearDayLogCache or remote logout Restoring --> Clearing: newer restore or clear bumps generation Clearing --> Absent: WeakMap delete + reset queries LivePersisting --> LivePersisting: same user restore waits on ready

Restoring

Record is inserted before IndexedDB read finishes, so a concurrent clear can find waitForPendingPersists and not delete under a rewrite.

Live

Query cache events for persistable date keys dehydrate success data to IndexedDB. Auth queries and range queries are ignored.

Clearing

Unsubscribe → wait pending writes → delete namespace → reset mounted date observers → drop WeakMap entry. If disk delete fails locally, memory stays so logout can retry.

Restore path

SessionRestorationGate awaits this before mounting Dashboard. Hydrate publishes memory first; the sanitized rewrite is tracked in the background so slow IndexedDB does not block first paint.

Known-empty vs Empty vs missing

A persisted null for a date is a Known-empty day (confirmed absence). An Empty Day Log is a real aggregate with meals/weight possibly empty. An unloaded date is simply not in the QueryClient. Corrupt IndexedDB becomes an empty online cache, not an error screen.

Logout and other tabs

Header tracks server logout separately from IndexedDB deletion. Other tabs do not call DELETE again. They reset mounted observers and run onRemoteClear (clear session, navigate to signup-login).

Function map

Public API is small. Everything else is the restore/clear machinery.

Function Visibility What it does
restoreDayLogCache public Confirm-user restore: bump generation, replace previous owner, hydrate, background rewrite, subscribe.
clearDayLogCache public Local logout/account-change path. Throws on persist failure so Header can retry without repeating DELETE.
createDayLogCacheWriteGuard public Dashboard range writes: only publish if generation and active user still match.
isPersistableDayLogQuery public Only ["dayLogs", "YYYY-MM-DD"]. Range keys and auth keys never hit disk.
dayLogCacheStorageKey public IndexedDB key: calibrate:day-logs:<encoded userId>.
clearActiveCache internal Ordered teardown of one WeakMap record.
subscribeToPersistence internal Dehydrate success date queries on add/update/remove.
applyRemoteDayLogCacheClear internal Other-tab handler: retry disk delete, always reset observers, then onRemoteClear.
clearPersistedNamespace / retryClear… internal Single-flight Map per storage key; remote path retries 3 times.
resetAndRemoveDayLogQueries internal query.reset() on date keys so mounted observers drop data, then removeQueries.
createPendingPersistenceTracker internal Set of in-flight persist promises; wait() drains them before delete.
sanitize / isUsable / discard internal Buster, schema, date-key match, 30-day window. Bad blobs are deleted, not shown.
createIndexedDbStorage internal Tiny native IDB adapter. No extra storage library.

What it deliberately does not do

  • Does not persist cookies, tokens, or authenticatedSession.
  • Does not queue offline Food Entry writes.
  • Does not own ETag / overlap revalidation (later tickets).
  • Does not keep two users’ namespaces hydrated on one QueryClient.
